# 0001 — 设备日志存 Flash（LittleFS）+ 唤醒周期末统一上传树莓派

## 状态

accepted（2026-08-30）

## 决策

主设备（ink-display-wifi-epd）维护一份"黑盒"事件日志：每次开机记录复位/唤醒原因
（`esp_reset_reason()`，跨重启保留——brownout/看门狗/panic 都能事后知道），运行中
关键事件（WiFi、授时、取图、舵机、刷屏、Web 端点调用）即时追加到 Flash（LittleFS，
复用 Default 分区方案里已有的 spiffs 分区，不动分区表、不擦 NVS）。

上传挂在 `goDeepSleepMinutes()` 这唯一的入睡前咽喉点：每次唤醒周期结束前，把
"上传游标"之后的全部事件一次性 POST 到树莓派 `POST /api/device_log/<key>`
（JSONL），收到 200 才推进游标；失败保留、下次唤醒重传。本地日志 64KB 上限滚动，
服务器侧才是全量档案。

## 被否决的备选

- **全量镜像 DBG_PRINTF 串口输出**：写入量大、拖慢唤醒，且与串口重复；黑盒只需要
  事件骨架。
- **panic handler 里抢写 Flash**：panic 环境写文件系统有卡死/损坏风险；复位原因
  寄存器跨重启保留，开机补记一条 BOOT 事件即可覆盖 99% 的"为什么重启"问题。
- **RAM 缓冲睡前一次性 flush**：省写入次数，但掉电/崩溃丢整个缓冲——设备一天只
  唤醒 1~3 次、每次十几条 ~100B，写入磨损可忽略，即时落盘的"最后一条留得住"更值钱。
- **纯 NVS 存日志**：不动分区，但 key-value 模型不适合追加流水且容量小。
- **服务器主动拉取**：需要设备常驻 HTTP 服务，与深睡眠架构冲突。

## 后果

- 固件（1.33MB）超出 Default 分区的 1.2MB APP 上限，分区方案改用
  **No OTA (Large APP)**（APP ~2MB + SPIFFS ~2MB）；标准方案 NVS 偏移一致，
  正常烧录不丢配置，但换分区后 FS 分区偏移变化，旧 Flash 日志不延续
  （切换当时日志尚未启用，无实际损失）。
- 事件时间戳为"开机序号 + 相对毫秒"，绝对时间靠锚点事件（授时成功后的墙钟）由
  服务器换算；深睡清零 millis 不影响排序。
- 崩溃在唤醒周期中途时，本周期事件要等下次成功联网才上传——Flash 滚动保留兜底。
