# ESP32 静默恢复（Silent Resume）设计

> 日期：2026-11-01
> 状态：设计已确认（会话内评审），随实现同步落地
> 关联：`hardware/esp32/esp32-power-hardware.md`（供电改造记录，路线 A/B 待办）

## 一、背景与目标

适配器断电切到电池时，电池 pack「充电→放电」交接会让 5V 轨断几毫秒（根因见供电文档），整机重启。重启后固件走「手动唤醒」全流程，用户可感知 4 处：

1. `showNetworkInfoScreen` 用 IP 信息页覆盖屏上照片；
2. 舵机机械归零再回位（扫动）；
3. 照片重新下载 + 墨水屏全刷（多轮黑白闪烁）；
4. 3 分钟 Web 窗口 + 全套网络流程。

墨水屏双稳态（断电画面不丢）、舵机机械保持（`servo_init(bootAngle)` 首帧写回上次角度，不跳角），因此**静默重启在原理上可行**：重启后不碰屏、不动舵机、不重拉照片，用户应看到零变化。

定位：硬件路线 A/B 是根治手段；本设计是**纵深防御**，同时覆盖舵机堵转触发 F1 保险丝、插头松动、棕眼等其他掉电成因。

## 二、唤醒分类器

`setup()` 在 `journalBegin()` 之后立即分类，结果存 `g_wakeClass`：

| 类别 | 判定 | 行为 |
|---|---|---|
| `TIMER` | `esp_sleep_get_wakeup_cause() == ESP_SLEEP_WAKEUP_TIMER` | 现有定时流程，不动 |
| `SILENT` | `ESP_RST_BROWNOUT`（电源塌陷专属）；或 `ESP_RST_POWERON` 且 `pwrman` 关闭（默认） | 静默恢复路径 |
| `MANUAL` | 其余全部：软复位/panic/看门狗；`ESP_RST_POWERON` 且 `pwrman` 开启 | 现有手动流程（信息屏 + 舵机归零 + 3 分钟窗口） |

**pwrman 开关（上电手动唤醒，方案 B 回退）**：NVS `dashcfg/pwrman`，默认关闭（全静默）。设备 `/debug` 页与 server 控制台均可切换，恢复出厂随 `dashcfg` 清除。开启后上电/复位走老契约（信息屏 + 舵机归零 + 3 分钟窗口）。

**2026-11-01 实测修订（原设计魔术字方案不成立）**：EN 复位是全芯片复位（串口横幅 `rst:0x1 POWERON_RESET`），RTC 慢内存同样不保留，`RTC_NOINIT` 魔术字在 EN 按压后丢失——EN 按压与真上电在固件层面**不可区分**。同日真机证据：掉电类故障（USB 供电在墨水屏电荷泵 + WiFi 满功率叠加下瞬间塌穿）重启原因正是 `POWERON` 而非 `BROWNOUT`。因此最终语义选择「POWERON 默认静默」（用户核心诉求），并提供 pwrman 开关保留老契约出口。

**前置条件（已撤销）**：原设计要求 `RTC_SLOW_MEM` 深睡保持供电以存活魔术字；魔术字移除后已恢复 `OPTION_OFF`，维持原深睡功耗优化。

## 三、静默恢复路径时序

```
journalBegin（已有，含复位原因） → 分类 = SILENT
→ servo_init(bootAngle)（保留，防跳角）→ 跳过归零 / 信息屏 / 常规照片拉取
→ WiFi 连接（沿用现有两轮扫描重试逻辑；不可达 → 置重试标记睡 30 分钟，不进配网）
→ syncTime() 局域网授时优先、NTP 回退（复用现有函数）
→ journalUpload()（GLITCH/BOOT 事件上报，控制台可见）
→ 当日补拉（§五 catchup，如触发）或花屏补刷（§四，如触发）；两者皆无 → 屏零动作
→ 隐形窗口 75s（RESUME_WINDOW_MS）：Web 服务在线 + registerDeviceWithServer()，
   期间屏、舵机、照片零动作；g_alwaysOnMode=true 则忽略时限直接进常开主循环
→ sleepUntilNextSchedule() 回睡（无时间或补拉失败 → 30 分钟重试，见 §五）
```

## 四、花屏修复（条件触发）

断电恰好撞上墨水屏刷屏会留花屏/半刷画面。方案：

- `displayFramebuffer()` 刷屏前在 NVS（`dashcfg` 命名空间，恢复出厂随之清除）置位「刷屏中 idx=N」，`EPD_DeepSleep()` 成功后清除；
- 静默启动发现标记仍在 → 重拉该 idx（`idx ≥ DAILY_PHOTO_COUNT` 退 0；下载失败则清除标记放弃，等每日刷新兜底，避免反复折腾电池）→ 补刷一次 → 走正常静默流程；
- 代价：每次刷屏 2 次 NVS 写（磨损可忽略）；只有真撞上刷屏中断电才多一次下载 + 全刷。

## 五、无时间重试与错过刷新日补拉

**无时间短周期重试**：掉电常伴随同一场停电（路由器/树莓派也没电），WiFi + 授时全失败。现有兜底盲睡 1440 分钟会错过刷新点；改为 NVS 置位「静默无时间重试」标记 + 睡 30 分钟，醒来（TIMER 唤醒 + 标记有效）重分类为 SILENT 再试；拿到时间即清标记、按 `refresh_hour` 排程。MANUAL 启动清除该标记（用户介入后恢复正常语义）；恢复出厂随 `dashcfg` 清除。

**错过刷新日补拉（catchup）**：停电跨越 `refresh_hour` 时（如 23:00–09:30），重试成功后若直接回睡，当日照片会漏刷、旧照片多留一天。新增 NVS「最后成功渲染日」（UTC 日序号，每次 `downloadAndRenderDailyPhoto` 成功后写入）：静默路径拿到时间后，若「最后渲染日 ≠ 今天 且 当前已过 refresh_hour」→ 走一次正常拉取（画面内容是当日新照片，这次闪刷是应得的），否则零动作回睡。

## 六、常开模式

- 静默 + 常开：直接进常开主循环，跳过初始照片重拉（屏上已是最新），下次拉取由 `nextDueEpoch` 对齐到 `refresh_hour`；
- 窗口时限：常开开启即忽略（现有 `if (g_alwaysOnMode) break;` 语义）；
- 进入常开前盖 RTC 魔术字，常开期间按 EN 仍走手动流程（现状行为）。

## 七、错误处理

- 静默路径任何失败不进 AP 配网；仅 `g_cfg.valid` 为假（新设备/恢复出厂）才走配网，优先级不变；
- WiFi 失败：不补花屏（标记保留至成功或放弃逻辑接管）、不上传日志（事件留 Flash，`goDeepSleepMinutes` 内 `journalUpload` 会自行跳过）、按 §五 重试回睡；
- 烧录新固件后的第一次启动魔术字无效 → 静默；开发时按一下 EN 即进手动窗口。

## 八、测试验收

1. 串口/device_log 验证三类启动各自命中；**实测 EN 按压后魔术字保留**（决定是否回退）；
2. 舵机动作中、刷屏中分别拔适配器 20–30 次：屏内容不变、舵机不动、日志出现 GLITCH 事件、窗口期内控制台可见设备上线；
3. 人为刷屏中断电 → 下次静默启动补拉重刷；
4. 模拟停电：拔适配器 + 路由器断电 → 30 分钟重试循环；路由器恢复后归位到 `refresh_hour` 排程；跨越 `refresh_hour` 的停电 → 恢复后补拉当日照片；
5. 回归：定时唤醒、EN 手动唤醒、配网、常开开关、server 控制台代理、`/fetch` LAN 推送；
6. 文档同步：CONTEXT.md「手动唤醒」定义与新增「静默恢复」词条、`esp32-power-hardware.md` 验收清单。

## 十、实现决定（相对评审稿的落地细化）

1. **魔术字方案已废除（2026-11-01 实测）**：EN 复位=全芯片复位，RTC 内存不保留，与真上电不可区分——`RTC_NOINIT_ATTR` 魔术字及其深睡供电前提一并移除；最终分类语义见 §二（POWERON 默认静默 + pwrman 开关回退）；
2. **时间同步复用 `syncTime()` 全流程**：局域网授时本就是第一优先，失败才走 NTP——快路径自动生效，全量函数只在其后；不为静默路径单写授时分支；
3. **静默重试标记、刷屏标记、渲染日均放 `dashcfg` NVS 命名空间**：`clearConfigNVS()` 的 `prefs.clear()` 自动能清理，不留陈旧状态；
4. **新增事件类型 `GLITCH`**：静默恢复判定与重试、补拉动作、pwrman 切换均记 GLITCH 事件，控制台可检索；服务端对 `t` 无白名单校验，安全；
5. **复位原因可读名导出**：`device_log` 新增公开 `journalResetReasonName()`，GLITCH 事件携带 `POWERON/BROWNOUT` 可读名；
6. **WiFi 不可达时不进 AP 配网**：静默恢复 + 全部已存网络不可见（停电把路由器也带走的典型场景）会命中现有「两轮全败 → 配网」分支，那会开热点并刷提示页（肉眼可见）；静默路径改为置重试标记直接回睡；
7. **当日补拉（catchup）**：停电跨越 `refresh_hour` 后，重试成功若直接回睡会漏掉当日照片（旧图多留一天）。新增「最后渲染日」NVS 记录（照片渲染成功路径写入），静默恢复拿到时间后发现漏日且已过刷新点 → 补拉一次（见 §五）；
8. **pwrman 开关双入口**：设备 `/debug` 页（`state=pwr_on|pwr_off`）+ server 控制台 `/api/device/debug` 转发，设备 `/api/status` 增加 `pwrman` 字段供控制台显示状态。
